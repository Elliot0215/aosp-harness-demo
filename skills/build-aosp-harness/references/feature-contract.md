# 把需求写成 feature 契约

生成 feature 上下文、`repos.tsv` 和验证断言时使用。下面的字段是写作骨架；落地时替换为实际事实，未知项写明原因和解决入口。

## Feature 上下文

一个 feature 文件集中表达树级约束与跨仓协作关系；已有分层指令时保持其有效性，不重复抄录整份手册。

```markdown
# <feature> 开发上下文

## 目标与完成条件
用户可观察的行为、兼容要求、非目标。
验收编号与验证脚本中的断言对应。
小需求满足自身验收与必要回归；独立审查仅在用户要求或项目规则要求时成为完成条件。
整个 feature 满足全部小需求和严格整体验收，不因前项交付而隐藏后项未完成。

## 环境与选择依据
源码根、Android/厂商版本、客户端版本。
feature 名、锚点仓或显式选择机制、预期分支。
产品/variant、构建入口；未知配置注明待配置。

## 范围与源码依据
repos.tsv 是涉及仓清单的事实源。
每仓说明路径、关键符号、负责行为及跨仓依赖。
区分已确认源码与需要进一步核实的假设。

## 开发约束
保留既有指令；写明本 feature 特有的 API、ABI、权限、构建约束。
不修改生成物；不扩展到清单之外的仓，除非需求和影响面已更新。

## intent 协作（用户明确要求时）
规划位置优先级：用户明确指定 → 已有资料 → feature/.intent/ → intent 默认。
一份 roadmap.md，展开需求使用固定编号的 Markdown，实际审查按轮次写入 review/ Markdown。
仅保留规划入口；主 agent 可更新这些规划资料，不扩大业务源码范围。
需求记录目标与验收、涉及仓子集及路径和理由、流程 skill、构建与验证入口、环境依赖、共享资源和实际证据。
源码根、Git project 根、规划目录分别识别；同一 out/、设备、CVD 组串行。

## 流程路由
改动条件 → 本地 skill 路径/名称 → 构建目标 → 验证入口。
列出真实存在的文件，不能指向尚未创建的 skill。

## 验证与证据
离线验证命令、真实验证命令、设备前置条件。
每条必需断言、预期值、日志/证据位置、失败和缺环境的判定。
只有无跳过的 RESULT PASS 且退出 0 才是严格通过。
```

把需求中的数字、权限边界、开关默认值和兼容要求保留为断言参数；不要改写为笼统的“功能正常”。

## 涉及仓清单

新 Harness 可采用 Codex / Cursor 示例的三列格式，使用实际 Tab 分隔，`#` 开头为注释。Claude 示例现有清单是空白分隔的仓路径、约定文件、标签、说明，检查器只读取第一列；复用时保留各端现有清单与检查器，不为 intent 协作统一 schema；只有用户另行要求修改格式时才同步迁移解析器和测试。

```text
# repository<TAB>feature<TAB>description
frameworks/base<TAB>dev-example<TAB>系统服务与调用入口
system/sepolicy<TAB>dev-example<TAB>服务访问标签和策略
```

`<TAB>` 仅用于说明，生成文件时写入真正的制表符。仓路径相对 AOSP 树根，必须解析到树内的 project；拒绝绝对路径、`..` 越界路径及解析后逃出树的符号链接。检查 project 自己的 `.git` 和顶层目录，避免 Git 向父目录查找而误把普通子目录识别为独立仓。拒绝重复路径、空清单、空字段和多余列。

沿用 Codex 三列格式时每行预期分支与 feature 目录同名，名称采用 `[A-Za-z0-9][A-Za-z0-9._-]*`。用户已有 `feature/foo` 等分支或多仓不同分支策略时，不悄悄改名：定义安全目录名到真实分支的显式映射，同步修改选择器、清单 schema、检查器和测试。未校验的分支名不能直接充当路径组件；校验后的安全单组件 feature 名可构造目录路径，仍需检查解析后未越界。分支名始终作为数据传参，不能拼成 shell 代码执行。

## 从行为形成验收表

例如用户需求是“系统边栏支持开关，关闭后输入行为恢复”，可拆为：

| 断言 | 数据或操作 | 预期与失败条件 | 环境 |
| --- | --- | --- | --- |
| 服务可用 | 精确查询服务注册与接口 | 注册存在且接口调用成功；查询失败即 FAIL | 设备 |
| 开关生效 | 切换开关并观察界面/状态 | 开启显示、关闭消失；仅进程存在不够 | UI 测试或设备 |
| 输入恢复 | 关闭前后执行同一坐标用例 | 目标控件收到预期事件；保留可比证据 | 设备 |
| 权限约束 | 合法和未授权调用方分别调用 | 授权调用成功、未授权访问被拒绝 | 测试调用方 |
| 稳定性 | 从本次操作基线查询相关 crash/AVC | 无新增相关错误；查询失败即 FAIL | 设备 |

这张表只演示推导方法，不能成为所有 AOSP 需求的固定用例。纯构建集成任务可能以产物、依赖与安装路径为验收；无需强加系统服务或 UI 检查。

尚未有可靠自动化方法的必需检查保留为 SKIP / INCOMPLETE，并说明需要什么证据。手动证据若允许参与验收，明确操作者、步骤、目标、时间和结果，不能由脚本默认填写通过。
